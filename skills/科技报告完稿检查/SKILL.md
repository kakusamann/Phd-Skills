# 科技报告完稿检查 Skill

## 1. Skill 目标

本 Skill
用于对课题或子课题科技报告开展完稿前的系统性审查，识别报告中与任务书不一致、职责边界不清、研究表述不准确、文风不规范、文献引用有误以及图表格式不符合科技报告习惯等问题。

本 Skill
的核心任务是**审查并提出修改意见**，不是擅自重写或修改整份报告。除非用户明确要求修改原文件，否则只输出问题清单和建议文本。

审查应遵循以下原则：

1.  **以用户提供的正式材料为依据。**
    任务书、项目记忆、正式报告、已发表论文及专利证明材料等是判断依据。
2.  **忠于任务书。**
    研究任务、关键词、成果名称、考核指标和年度节点应尽量沿用任务书的正式表述。
3.  **明确职责边界。**
    不将其他课题或子任务承担的模型研发、技术开发、平台建设等工作写成本子课题独立完成的成果。
4.  **区分事实错误与文风优化。**
    明确标注必须修改的问题和可优化的问题，避免将个人语言偏好当作硬性错误。
5.  **不擅自扩展审查范围。**
    用户只要求检查某一项时，只完成该项，不附加其他审查、设计或修改任务。
6.  **不臆造信息。**
    无法从材料中确认的事实、文献元数据、成果状态或页码，应明确标注”待核实”。

------------------------------------------------------------------------

## 2. 输入材料

开始审查前，优先确认以下材料是否齐备：

| 输入材料                   | 用途                                             | 缺失时的处理                                   |
|:---------------------------|:-------------------------------------------------|:-----------------------------------------------|
| 最新版科技报告（DOCX/PDF） | 本轮审查对象                                     | 必须取得；若存在多个版本，确认哪一份是最新版   |
| 正式任务书                 | 核对任务、指标、成果名称、年度节点和术语         | 未提供时，不得声称已完成任务书一致性审查       |
| 项目记忆或项目组织分工材料 | 确认项目结构、各课题及子任务的承担单位和职责边界 | 仅按已提供的材料判断；不推测组织分工           |
| 参考文献原文、DOI或文献PDF | 核验引用准确性和出版状态                         | 无法验证的文献标记为待核实                     |
| 成果证明材料               | 核验论文、专利、软件著作权等成果信息             | 不根据不完整截图补造作者、卷期、页码或授权信息 |
| 上一版报告（可选）         | 判断本轮整改是否完成、是否引入新问题             | 无需为了比较而强制要求                         |

### 2.1 版本确认

- 以用户明确指定的最新版为唯一审查对象。
- 不将旧版本中的问题自动认定为新版本仍然存在。
- 如文件名、上传时间或内容无法确认版本，应先询问用户，不自行选择。
- 审查过程中记录文件名称、版本和可读取的页数。

### 2.2 材料优先级

出现信息冲突时，按以下顺序处理：

1.  正式任务书及其正式变更文件；
2.  项目正式组织分工、任务分解或经确认的项目文件；
3.  已经确认的实际研究记录和成果证明；
4.  当前科技报告中的自述；
5.  模型的一般知识或经验判断。

报告中的自述不能单独作为证明其符合任务书或成果已经完成的依据。

## 3. 总体工作流程

按照以下顺序执行，避免只做语言润色而遗漏实质性问题。

### 第一步：确认审查对象和范围

1.  确认最新版报告文件。
2.  确认任务书、项目记忆和相关成果证明是否可用。
3.  明确本次审查范围：全面完稿检查，还是仅检查某一专项。
4.  若用户只要求某一专项，严格限定在该专项内。

### 第二步：建立任务书对照基准

从任务书提取并整理：

- 课题及子课题名称；
- 研究目标；
- 研究内容和任务分解；
- 技术路线及关键技术；
- 年度任务和阶段节点；
- 考核指标；
- 预期成果名称、数量和形式；
- 任务书中的固定术语和关键词；
- 各参与单位或子任务的职责分工。

形成内部对照表，供后续逐章核对。不得用模型自行概括的表述替换任务书正式用语。

### 第三步：核查叙事逻辑和职责边界

按”项目任务—子课题定位—年度研究目标—研究内容—技术路线—年度进展—研究结论—成果—下一年度计划”的顺序核查。

重点判断：

- 报告是否准确体现本子课题在整个项目中的定位；
- 是否把前置课题提供的技术成果写成本子课题自主研发成果；
- 是否把其他子任务负责的模型或平台研发写成本子课题直接完成；
- 是否把”集成、调用、整合、优化、形成方案”夸大为”自主研发、开发完成、工程实现”；
- 是否将尚未完成的工作写成已完成；
- 是否将阶段性成果写成最终成果；
- 是否将下一年度计划写成当年已完成任务；
- 是否与任务书的年度节点和考核要求一致。

### 第四步：核查文献引用

检查正文引文、参考文献表和原始文献之间的对应关系，具体见第 6 节。

### 第五步：核查科技报告文风和术语

重点检查概念标签式表达、破折号串联、口号式语言、空泛表达、术语不统一和不符合科技报告习惯的句式，具体见第
7 节。

### 第六步：全面核查标点符号

逐页检查正文、表格、图题、表题、注释、参考文献及可读取的图中文字，具体见第
8 节。

### 第七步：核查图表及清单

逐项提取图题、表题和正文交叉引用，检查编号连续性、标题位置、图清单和表清单，具体见第
9 节。

### 第八步：形成问题清单并复核

1.  按报告出现顺序排列问题。
2.  标注准确页码和章节/表格位置。
3.  提供原句、问题分析和修改建议。
4.  区分必须修改与建议优化。
5.  不将无法确认的问题写成确定错误。
6.  用户完成修改后，只对修改后的最新版进行复核，不重复输出已经解决的问题。

## 4. 任务书一致性与子课题职责边界

### 4.1 研究目标和任务表述

核对科技报告中的以下内容：

- 本年度研究目标；
- 研究内容和研究方法；
- 关键技术和技术路线；
- 年度任务完成情况；
- 本年度研究结论；
- 成果统计；
- 下一年度工作计划。

逐项对照任务书，检查是否存在：

- 任务书关键词被替换成含义不同的词；
- 任务书规定的任务被遗漏；
- 报告新增了任务书没有要求且没有实际依据的研究任务；
- 研究目标、研究内容和结论之间不对应；
- 年度任务和成果指标的完成状态表述不准确；
- 任务书中的”初步形成”“完成框架整合与优化”“形成方案”等阶段性表述被夸大。

### 4.2 职责边界核查

对于由多个课题或子任务协作完成的项目，必须建立”成果来源—承担方—本子课题使用方式”的关系。

建议采用以下判断方式：

| 实际工作关系               | 推荐表述方向                           | 应避免的表述                         |
|:---------------------------|:---------------------------------------|:-------------------------------------|
| 其他课题提供筛查成果       | 集成、采用、结合、衔接筛查成果         | 本子课题完成污染物筛查研发           |
| 其他课题提供预测模型       | 集成模型、调用模型、明确接口和应用需求 | 本子课题研发并完成预测模型           |
| 其他子任务提供预警模型     | 结合相关子任务模型成果开展方案集成     | 本子课题独立开发预警模型             |
| 其他子任务承担平台软件开发 | 提出平台功能需求、接口要求和集成方案   | 本子课题完成平台软件开发             |
| 本子课题承担系统性解决方案 | 整合、优化、编制系统性解决方案         | 将全部底层技术研发均归为本子课题成果 |
| 后续课题承担工程示范       | 为工程示范提供方案支撑、配合应用验证   | 将尚未开展的工程示范写成已完成       |

上述表格是判断逻辑，不是对所有项目的固定分工。具体职责必须以用户提供的任务书和项目组织材料为准。

### 4.3 阶段状态用语

必须区分：

- 已完成；
- 初步形成；
- 正在开展；
- 已完成方案设计；
- 已完成模型或平台研发；
- 已完成工程应用验证；
- 计划开展。

不能仅为匹配任务书而把”初步形成”改成”完成”，也不能把”提出接口要求”写成”完成软件开发”。

### 4.4 芯片子课题示例中的固定口径

对于本项目子课题
4.4（芯片），在正式任务书和项目记忆仍适用的前提下，应特别注意：

- 子课题 4.4
  的重点是芯片生产全过程环境风险防控系统性解决方案的集成、整合、优化与编制。
- 前置课题提供的新污染物筛查、污染物释放预测、风险削减和优化控制等技术成果，应按实际来源表述。
- 课题 4
  内其他子任务承担的风险预警模型、平台软件等成果，应明确为相关子任务成果，再由
  4.4 开展集成衔接。
- 后续工程示范工作应根据任务分工表述，不得提前写成 4.4 已经独立完成。
- 风险分层统一使用”点—面—汇”。这是该方案的指定术语，不应因一般文风审查而改写为其他形式。

此示例仅适用于上述项目，不可机械套用到其他项目。

## 5. 研究内容、年度进展和成果表述核查

### 5.1 目标—内容—结果闭环

检查以下关系是否成立：

| 部分         | 核查问题                                       |
|:-------------|:-----------------------------------------------|
| 研究目标     | 本年度计划解决什么问题？是否来自任务书？       |
| 研究内容     | 实际开展了哪些研究工作？是否覆盖研究目标？     |
| 技术路线     | 采用什么方法、数据和技术实现研究内容？         |
| 年度进展     | 本年度实际完成到什么程度？是否有证据？         |
| 研究结论     | 是否能够由研究内容和实际结果支撑？             |
| 成果统计     | 是否与本年度实际形成的论文、专利、软件等一致？ |
| 下一年度计划 | 是否承接尚未完成的任务，且符合任务书节点？     |

### 5.2 研究成果核查

论文、专利、软件著作权、标准、报告等成果应逐项核对：

- 成果名称是否准确；
- 作者、申请人或权利人是否准确；
- 期刊、专利号、申请号、授权公告号等是否准确；
- 发表、录用、公开、实质审查、授权等状态是否准确；
- 是否确实标注或归属该项目；
- 是否属于本年度统计范围；
- 是否与任务书成果指标对应。

专利必须区分申请、公开、实质审查和授权。不得将”公开”误写成”授权”，也不得仅凭申请号判断授权状态。

### 5.3 结论与计划

- 结论只总结已有工作和已有证据。
- 下一年度计划使用未来时态或计划性表达。
- 不在结论中把计划工作写成已完成成果。
- 对模型精度、风险削减效果、工程应用效果等定量结论，必须确认报告提供了对应数据或证明材料。

## 6. 文献引用与参考文献核查

### 6.1 正文引文与参考文献表对应

至少完成以下四项检查：

1.  正文中每一条文献引用都能在参考文献表中找到对应条目。
2.  参考文献表中的每一条文献都确实在正文中被引用；如项目要求允许列出延伸阅读文献，则按其要求处理。
3.  同一文献在正文不同位置的作者、年份和引用标号保持一致。
4.  不存在引用标号错位、漏号、重复标号或一条引文对应错误文献的情况。

如果报告采用数字顺序编码制，建立”引用标号—参考文献条目”映射表；如果采用作者—年份制，核对作者拼写、年份及同年文献区分标识。

### 6.2 文献元数据准确性

对可验证的文献，逐项核查：

- 标题；
- 作者及作者顺序；
- 发表年份；
- 期刊名称；
- 卷、期；
- 页码或文章编号；
- DOI；
- 发表状态。

优先使用出版社页面、期刊官网、Crossref 或文献原文核实。DOI
解析结果与文章元数据应相互印证。

不能只凭标题相似就认定文献正确。无法取得原文或可靠元数据时，标记为”待核实”，不补造信息。

### 6.3 引用准确性与相关性

不仅检查格式，还要判断文献是否支持引用所在句：

- 文献研究对象是否一致；
- 文献是否支持该句所述结论；
- 文献是否支持所引用的具体污染物、工艺、风险或技术；
- 是否将综述性结论错误归因于单篇研究；
- 是否存在引用年份、研究区域或研究对象不匹配。

如需要评价文献是否支持论述，应阅读摘要、正文或相关章节，不应仅凭题名判断。

### 6.4 引用位置和遗漏

- 文献引用应放在其所支持的完整语义单元之后，避免插入主谓宾结构中间。
- 一个句子包含多个不同事实时，必要时分别安排引用。
- 对连续列举的多个事实，不应将所有引用无差别地集中到句末，导致无法判断各文献支持哪项事实。
- 检查正文中有事实陈述但缺少必要依据的情况；只有在用户要求检查引用完整性或文献支持性时，才提出补充引用建议。

### 6.5 参考文献格式

以用户或项目组指定的格式为准。

若要求参考 Bioresource Technology（BT）期刊格式：

- 优先在 Zotero 中选择对应官方 CSL 样式；
- 不擅自修改 CSL；
- 若项目组暂未要求定制格式，先使用官方 Zotero 样式；
- 对期刊名缩写或全称、DOI
  是否显示、标点、作者格式等差异，先记录并等待项目组统一要求，不擅自更改用户已确认的方案；
- 若项目组后续提出”期刊全称”“不显示 DOI”等要求，再按要求调整 CSL
  或统一格式。

不能将某一报告往年的排版习惯自动视为本年度唯一强制格式，除非项目组明确要求沿用。

## 7. 科技报告文风与术语审查

### 7.1 概念标签式破折号表达

重点搜索类似以下结构：

- “A—B—C”；
- “A—B—C—D”；
- 多个名词或动词通过破折号连接，形成概念标签串联。

判断是否需要修改时，区分两类情况。

**通常需要检查或改写的情况：**

- 用多个概念标签代替实际研究过程；
- 用阶段名称代替具体工作内容；
- 用口号式结构代替技术关系；
- 多个并列目标之间没有说明逻辑关系；
- 读者无法从句子中判断具体做了什么。

改写方向：

| 标签式表达           | 推荐表达方向                                       |
|:---------------------|:---------------------------------------------------|
| A—B—C全过程          | 说明具体覆盖的工作环节                             |
| 监测—识别—预测—预警  | 建立监测数据采集、风险识别和预测预警机制           |
| 调查—筛查—评价       | 开展基础调查，整合筛查结果，并据此进行评价         |
| 感知层—数据层—模型层 | 由感知层、数据层和模型层组成                       |
| 源头—过程—末端       | 根据实际内容写明污染物产生、生产过程控制和末端治理 |

**不应机械修改的情况：**

- “点—面—汇”等任务书或方案明确规定的专有术语；
- 编号范围、时间范围、数值区间；
- 已经约定俗成且含义明确的专业术语；
- 用户明确要求保留的表达。

改写应保留技术含义，不要为了消除破折号而引入新的技术内容。

### 7.2 口号式、空泛和堆叠表达

重点检查：

- “实现从……向……跃迁/转变”等缺乏具体内容的句子；
- “赋能、支撑、引领、全面提升、系统突破”等泛化词语；
- “多维度、全方位、全过程、跨尺度、跨介质”等连续堆叠；
- 连续罗列大量名词或动词，却没有说明它们之间的关系；
- “构建体系、形成机制、建立平台”等表述没有明确对象和实际内容。

处理原则：

1.  尽量明确研究对象、技术动作和结果。
2.  用简短陈述句代替宣传性表达。
3.  不删除有实际意义的技术术语。
4.  不把必要的专业概括全部改成冗长解释。

### 7.3 术语一致性

建立全文术语表，检查同一概念是否出现多个名称或缩写。

重点核对：

- 任务书中的正式名称；
- 课题、子课题和承担单位名称；
- 优先控制新污染物等正式术语；
- 风险对象层级和技术架构名称；
- 污染物、工艺、治理设施及模型名称；
- 图表标题与正文中的名称；
- 缩写首次出现时是否给出中文全称或英文全称（按报告规范）。

对于本项目，统一采用”点—面—汇”，不得混用”点—线—面”。

## 8. 标点符号全面检查

必须逐页检查正文、表格、图题、表题、脚注、注释、参考文献以及可读取的图中文字。不能只依赖全文搜索；对表格和图像内容，应尽可能查看页面渲染结果。

### 8.1 重复、缺失和配对错误

检查：

- 连续重复的句号、逗号、顿号、分号；
- 句末同时出现句号和分号；
- 句末连续两个句号；
- 孤立的顿号、逗号、冒号或分号；
- 句子缺少必要的句末标点；
- 括号、引号、书名号未成对；
- 中文括号和英文括号不匹配；
- 标点放在括号内外的位置不合理；
- 列表末项标点与前面项目不一致。

### 8.2 中文和英文标点混用

按语境区分：

- 中文正文优先使用中文全角标点；
- 英文题名、英文参考文献及英文原文内部标点按对应规范保留；
- DOI、网址、文件路径、代码、化学式和专业缩写中的标点不应强行改成中文标点；
- 中文正文中的英文文献作者—年份引用，按报告当前选定的引用样式保持一致。

### 8.3 顿号、逗号和分号层级

- 顿号用于较短的并列词语或短语。
- 逗号用于句内停顿和分句之间的一般连接。
- 分号用于较长、结构相对独立的并列分句。
- 同一层级的并列项目应保持标点形式一致。
- 多层并列时，明确内外层级，不要将顿号、逗号和分号混用到无法判断结构。

### 8.4 冒号

检查冒号是否确实用于引出解释、列举、说明或引用。

以下情况通常不需要冒号：

- 独立章节标题，如”参考文献”；
- 普通句子中不具有引出关系的位置；
- 冒号前后没有形成合理的解释或列举关系。

### 8.5 加号、斜杠及其他符号

重点检查 `+`、`/`、`&` 等是否被当作中文连接词使用。

| 表达情况                   | 处理原则                                         |
|:---------------------------|:-------------------------------------------------|
| “混凝沉淀+微滤处理”        | 若表示工艺组合，正文可改为”经混凝沉淀和微滤处理” |
| “电热水洗/等离子水洗”      | 若表示二选一，改为”电热水洗或等离子水洗”         |
| “含氟/含氯污染物”          | 若表示并列，改为”含氟和含氯污染物”               |
| VMB/VMP、VOCs/NMHC         | 专业缩写组合，确认含义后可保留                   |
| Ca/F                       | 若表示化学计量比或元素比，保留并核对上下文       |
| 文件路径、网址、公式和代码 | 按其技术格式保留                                 |

不得无差别替换所有斜杠或加号。必须判断符号在具体语境中承担的是专业含义还是中文连接功能。

### 8.6 数字、单位和编号

检查：

- 数字与单位之间的空格是否符合所采用规范；
- 数值范围连接符是否统一；
- 日期范围和年度区间格式是否一致；
- 小数点、百分号、温度、频率等符号是否正确；
- 章节编号、条目编号和表格编号格式是否一致；
- 阿拉伯数字编号后是否按报告格式保留空格；
- 编号范围与类别名称之间是否有必要的分隔。

不要将合法的负号、范围连接符、化学式符号或设备编号误判为标点错误。

### 8.7 参考文献标点

参考文献作为独立格式体系核查：

- 作者之间的分隔符；
- 作者与年份之间的标点；
- 题名、期刊名、卷期、页码或文章编号之间的标点；
- DOI 前后的标点；
- 中英文参考文献格式是否符合指定样式。

不要仅为了让中文和英文参考文献外观一致而破坏选定的 CSL
样式。应先确认项目组指定的著录标准。

## 9. 图、表及图表清单检查

### 9.1 提取完整图表清单

从正文、图题、表题和目录中逐项提取：

- 图编号；
- 图名称；
- 图所在页码；
- 表编号；
- 表名称；
- 表所在页码。

清单应保留报告中的原始编号和标题，不得自行润色或改名。

建议输出格式：

#### 图清单

| 图编号 | 图名称   | 所在页码 |
|:-------|:---------|:--------:|
| 图1.1  | 原文图题 |    10    |

#### 表清单

| 表编号 | 表名称   | 所在页码 |
|:-------|:---------|:--------:|
| 表1.1  | 原文表题 |    12    |

页码应注明是 PDF
实际页码还是报告印刷页码；两者不一致时应说明采用哪一种。

### 9.2 图题和表题的位置

这是必须检查的排版规则：

- **图题放在图的下方。**
- **表题放在表的上方。**

具体检查：

1.  图题是否紧跟对应图片，位于图片下方。
2.  表题是否紧跟对应表格，位于表格上方。
3.  图表题是否与对应图表处于同一逻辑位置，避免分页导致标题与对象分离。
4.  表格跨页时，续页是否按报告规范重复表头或标注”续表”。
5.  图题、表题的编号、字体、字号、居中方式和标点是否统一。
6.  图表题是否准确概括图表内容，与正文引用名称一致。

不能将表题放在表格下方，也不能因为图题在下方而将表格题也放在下方。

### 9.3 编号连续性

按章节编号规则检查：

- 是否从图1.1、图1.2等连续编号；
- 是否出现重复编号；
- 是否存在跳号；
- 图和表是否分别独立编号；
- 章节变化后是否正确重置编号；
- 正文引用的编号是否与图表题一致。

如报告采用全篇连续编号，则按全篇规则检查，不得擅自改成章节编号。

### 9.4 正文交叉引用

逐项检查：

- 正文中出现的”如图X.X所示”是否存在对应图；
- 正文中出现的”如表X.X所示”是否存在对应表；
- 图表题是否在正文中被引用（如报告规范要求）；
- 正文引用是否指向正确的图表；
- 是否存在图表已删除但正文仍保留引用；
- 是否存在图表已插入但正文引用编号未更新。

### 9.5 图清单和表清单

如果报告要求设置独立的图清单和表清单：

- 图清单列出全部图编号、图名称和页码；
- 表清单列出全部表编号、表名称和页码；
- 图清单、表清单与正文图表逐项一致；
- 页码在排版更新后重新核对；
- 不得遗漏附录中的图表（如报告规范要求纳入）；
- 不得把正文中提及但未实际设置的示意图当作正式图表列入清单。

如果报告规范没有要求独立清单，不应擅自要求新增；可以将其作为可选完善建议。

### 9.6 图表检查结论

最终至少汇总：

| 核查项目         | 图               | 表               |
|:-----------------|:-----------------|:-----------------|
| 总数量           | 统计值           | 统计值           |
| 编号是否连续     | 正常/异常        | 正常/异常        |
| 是否有重复编号   | 是/否            | 是/否            |
| 是否有跳号       | 是/否            | 是/否            |
| 正文引用是否匹配 | 正常/异常        | 正常/异常        |
| 标题位置是否正确 | 图下方           | 表上方           |
| 清单是否完整     | 正常/异常/未设置 | 正常/异常/未设置 |

## 10. 问题输出格式

### 10.1 默认逐项格式

对于需要修改的句子，优先使用：

**\[1\] 位置：第X页，第X节/表X.X**

**问题句：**  
“报告原文。”

**问题分析：**  
说明具体问题、与任务书或规范的冲突，以及为什么需要修改。

**修改建议：**  
“建议替换为的完整文本。”

如属于非必须优化，应明确标注：

- `[必须修改]`：事实错误、任务书不一致、引用错误、编号错误、标点重复或图表位置错误等。
- `[建议优化]`：文风不够规范、表达略显冗长或可读性有待提升，但不构成事实或格式错误。

### 10.2 表格输出格式

当用户要求表格时，使用：

序号 位置 问题句 问题分析 修改建议 —— —— ——– ———- ———-

表格内容较长时，不要为了压缩而省略关键原句或修改文本。

### 10.3 专项清单输出

如果用户只要求某一专项，例如只检查破折号或只检查标点：

- 只输出该专项问题；
- 不附带其他未被要求的检查结果；
- 对专项中没有发现的问题，简洁说明”未发现明确问题”；
- 不要顺便开展文献、任务书、图表或其他审查。

### 10.4 图表清单输出

图表清单使用：

**图清单**

图编号 图名称 页码 ——– ——– ——

**表清单**

表编号 表名称 页码 ——– ——– ——

随后单独列出编号、交叉引用、标题位置和清单完整性核查结论。

### 10.5 修改建议要求

- 尽量提供可直接替换的完整句子。
- 只修改有问题的部分，不无故重写整段。
- 保留原文技术含义、专业术语、数据和责任主体。
- 不新增没有来源支持的研究结果、指标或成果。
- 同一问题在多处重复出现时，可给出统一修改规则，并列出所有位置。
- 修改建议应符合科技报告的简短、清晰、客观和可复核风格。

## 11. 证据、页码和核查边界

### 11.1 位置定位

每一项问题尽量提供：

- PDF 页码或 Word 页码；
- 章节编号；
- 表格编号或图表编号；
- 原文句子或单元格内容。

如果 PDF 实际页码与文档印刷页码不同，应明确标注页码口径。

### 11.2 证据原则

- 原文问题必须能在报告中定位。
- 任务书不一致必须指出对应的任务书依据。
- 文献错误必须有原始文献或可靠元数据支持。
- 图表编号错误必须通过图表标题和正文引用交叉核对。
- 不得根据截断的文件检索片段推断整句内容。
- 对无法读取的图片文字、扫描页或表格内容，明确说明未能核验。

### 11.3 无法确认的情况

以下情况应标注”待核实”：

- 文件版本不明确；
- 任务书没有提供；
- 文献无法访问原文或可靠元数据；
- 成果授权或发表状态缺乏证明；
- 图中文字无法辨认；
- 页码因排版变化而无法准确对应；
- 表格中的斜杠、加号等符号究竟表示并列还是工艺选择关系无法确定。

不能把”待核实”改写成确定性结论。

## 12. 禁止事项与范围控制

本 Skill 必须遵守以下限制：

1.  用户只要求检查某一项时，不擅自开展其他检查。
2.  未经用户明确要求，不直接修改、覆盖或重排原始科技报告。
3.  不擅自新增研究内容、技术路线、成果或参考文献。
4.  不把一般经验判断说成任务书的明确要求。
5.  不擅自改变项目正式术语、课题名称、成果名称和编号体系。
6.  不把其他课题或子任务的工作归入当前子课题。
7.  不将计划工作、方案设计或模型调用写成已经完成的研发或工程应用。
8.  不因追求语言简洁而删掉必要的技术限定条件。
9.  不机械替换所有破折号、斜杠、加号、括号或专业缩写。
10. 不将旧版本的问题直接复制到最新版，必须重新核验。
11. 不输出无法定位、没有原文依据的泛化批评。
12. 不在用户没有要求时生成额外的修改方案、PPT、Word或其他文件。

## 14. 最终报告格式建议

全面审查完成后，建议按以下结构输出：

1.  **审查对象与范围**：列明文件名称、版本、对照依据和检查范围。
2.  **总体结论**：概括是否达到完稿要求；区分必须修改项和建议优化项。
3.  **必须修改的问题**：按报告顺序逐条列出位置、原文、问题分析和修改建议。
4.  **建议优化的问题**：单独列出文风或格式方面的优化项。
5.  **图表清单与核查结果**：列出全部图、表及编号和位置核查结论。
6.  **待核实事项**：只列出确实缺乏材料或证据的问题。
7.  **最终整改清单**：简要汇总需要用户处理的项目。

如果用户只要求专项审查，则不使用上述完整结构，只输出该专项结果。

**最终原则：科技报告完稿审查的目标不是把文字改得复杂或华丽，而是确保任务准确、职责清楚、数据和文献可靠、术语统一、表达简洁、图表规范，并且每一项结论都能够追溯到相应依据。**
